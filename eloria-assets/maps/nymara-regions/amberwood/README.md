# Amberwood production map package

Amberwood is the amber-forest region on Nymara's western coast: an inhabited
old-growth autumn woodland on a rugged shoreline, centred on a water-linked
settlement, carrying the monumental Amber Gate on its central axis, and fading
eastward into burnt, barren country.

The region is authored at **576 m x 576 m** - three times its original linear
extent, nine times the area - on a 96 x 96-tile server map at one metre per
tile.

This directory is the runtime package plus everything needed to rebuild it.

## Runtime files

| File | What it is |
| --- | --- |
| `world.glb` | Self-contained glTF 2.0 scene: geometry, materials and every texture embedded. No external files, no glTF extensions. |
| `world.json` | GLB world manifest, schema version 1 — bounds, coordinate transform, spawns, collision and navigation declarations, landmarks, interactives, NPC and creature markers, harvestables, portals, roads, water, environment, minimap transform, provenance. |
| `world-lod2.glb` | Reduced package: far-tier vegetation only, no ground clutter, half-resolution textures. |
| `collision.bin` | Half-metre walkability grid, `EWCG` version 1, 1152 x 1152 cells over the server footprint. |
| `minimap.webp` | North-up minimap rendered from the final geometry, not drawn by hand. |
| `world.glb.validator.json` | glTF 2.0 validation report. |
| `verification-report.json` | Runtime contract report: grounding, navigation, collision and spawn checks. |
| `performance-summary.md` | Triangle, node, texture and package budgets. |

## Source

`source/` holds the complete authoring toolkit and the build entry points. It is
pure Python (numpy + Pillow) with one small C rasteriser used only for offline
previews. Nothing here imports a model, a texture or an asset pack: every
mesh and every texel in the package is generated by this code.

```sh
cd source
python3 build_amberwood.py          # writes the runtime package one directory up
python3 verify_runtime.py           # reproduces the client's grounding contract
python3 validate_gltf.py ../world.glb
python3 export_source_elm.py        # regenerates the 64x64 server ELM
python3 capture_views.py            # comparison captures
python3 compress_captures.py        # PNG -> WebP
python3 make_comparison.py          # concept/build comparison sheets
```

The build is deterministic: the same seed reproduces the same bytes. Runtime
startup never depends on rerunning it — the committed artefacts load directly.

## Coordinates

Right-handed, metres, Y up, north toward `-Z`. The server's 576-cell grid maps
at one metre per tile with the arrival datum at server `(174, 174)`:

```
godot_x = server_x - 174        godot_z = 174 - server_y
```

so the reachable footprint is `x ∈ [-174, 401]`, `z ∈ [-401, 174]`. Terrain is
cut larger than that on every side and the surplus is raised into mountain walls
or drowned, so a character cannot reach an unfinished void.

**This needs a matching server map.** `../source-elm/amberwood.elm` is
regenerated here at 96 x 96 tiles (576 x 576 height cells) with real elevation
and walkability, replacing the flat 32 x 32 placeholder. Load that server-side
and the client registry's existing `metresPerTile: 1.0` stays correct.

## Navigation contract

The Godot client turns every `MeshInstance3D` whose name begins with an entry in
`navigation.surfaceNodePrefixes` into collision on its navigation layer, then
grounds actors with a downward ray. This package uses two prefixes:

* `Terrain_` — the seven terrain surface classes.
* `Walk_` — authored walkable decks only: bridge decks, canopy platform floors,
  walkway planking, dock decking, stairs and the garden terrace steps.

Structural geometry is deliberately **not** a walk surface, so the grounding ray
never snaps a character onto the top of an arch, a roof or a tower.
`source/verify_runtime.py` casts that exact ray at all 331,776 reachable server
tiles and currently reports zero misses.
